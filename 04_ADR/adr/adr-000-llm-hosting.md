# ADR-000: Выбор способа хостинга LLM для «Умного помощника командировок» — облачный API (SaaS) вместо Self-hosted

* **Статус:** Принято
* **Дата:** 25 августа 2026 г.
* **Авторы:** Архитектор проекта «Trip Assistant»

---

## 1. Context (Контекст)

В проекте «Умный помощник командировок» (мультиагентная система: Supervisor + 6 воркеров на LangGraph, RAG по политике командировок на pgvector — ДЗ-03) требуется выбрать способ хостинга LLM. Возникла дилемма:

* **Вариант A:** проприетарная облачная модель по API (SaaS, класс GPT-5 / YandexGPT Pro);
* **Вариант B:** Open-Source модель **Llama 3 70B**, развернутая на собственных серверах (Self-hosted).

### Ограничения и движущие силы:

1. **Стадия MVP:** трафик не подтверждён — прогноз ~1 000 диалогов/день (~30–50 LLM-вызовов на диалог из-за агентного цикла и RAG).
2. **Чувствительные данные:** в промпты попадают PII сотрудников (имя, ранг, маршрут, даты, суммы) и фрагменты внутренней политики командировок.
3. **Агентные сценарии:** критичны tool calling (поиск билетов/отелей), структурированный вывод (JSON-смета), многошаговое планирование Supervisor'ом.
4. **Команда:** 2–3 ML-инженера, выделенной MLOps/Platform-компетенции для эксплуатации GPU-инференса нет.
5. **Бюджет:** операционные расходы (OPEX) предпочтительнее капитальных (CAPEX на GPU-парк не согласован).

### Результаты сравнительного анализа (полностью — в `../README.md`):

| Критерий | SaaS (GPT-5-класс) | Self-hosted (Llama 3 70B) |
|----------|:---:|:---:|
| Стоимость (MVP-этап) | **Выигрывает:** ~$3.6K/мес при прогнозе MVP, оплата по факту | Проигрывает: ≥ $7.9K/мес фикс (GPU + MLOps) при эквивалентной утилизации ~45% |
| Безопасность данных | Приемлемо при DPA + ZDR + маскировании PII | **Выигрывает:** данные не покидают периметр |
| Качество ответов | **Выигрывает:** лидеры агентных бенчмарков (tool calling, JSON) | Уступает в сложных агентных цепочках и на русском языке |
| Latency | Достаточно: TTFT 300–800 мс, стриминг | Сопоставимо: TTFT 100–300 мс, но нужны очередь и автоскейл |
| Сложность поддержки | **Выигрывает:** инфраструктура на провайдере | Проигрывает: vLLM, драйверы, on-call, найм MLOps |

Взвешенная оценка (ATAM): **SaaS 4.05 vs Self-hosted 3.15**.

---

## 2. Decision (Решение)

**Принять вариант A: облачная проприетарная LLM по API (класс GPT-5 / YandexGPT Pro) с обязательным контуром защиты данных.**

Конкретизация решения:

1. **Многоуровневая модель:** флагманский класс (GPT-5 / YandexGPT Pro) — только для Supervisor'а и формирования отчёта; лёгкие дешёвые модели — для воркеров (извлечение параметров, простые RAG-ответы).
2. **Обязательный security-контур (условие принятия):**
   * DPA с провайдером, режим Zero Data Retention (промпты не сохраняются после обработки, не используются для обучения) [3];
   * PII-маскирование до промпта: имена, номера документов, контакты заменяются токенами; де-маскирование только внутри периметра;
   * RAG-подсистема (pgvector, документы политики) остаётся внутри контура компании — наружу уходят только релевантные фрагменты после DLP-проверки;
   * Выбор провайдера с региональным endpoint (данные в юрисдикции РФ/ЕАЭС для российского контура — YandexGPT; либо Azure OpenAI в EU-регионе для международных).
3. **Защита от lock-in:** весь доступ к LLM — через единый шлюз-абстракцию (LangChain/LiteLLM-совместимый интерфейс), промпты и оценки — в репозитории; периодический (раз в квартал) прогон эталонных сценариев на альтернативной модели (включая self-hosted Llama) для сохранения миграционной способности.
4. **Триггеры пересмотра решения (checkpoint):**
   * стабильный трафик > 100M токенов/день в течение 2+ месяцев (≈60% порога безубыточности ~175M токенов/день — запас времени на миграцию, расчёт в `../README.md` §3);
   * утилизация эквивалентного GPU-парка прогнозно > 60%;
   * изменение регуляторных требований (запрет передачи PII внешним обработчикам);
   * появление в команде выделенной MLOps-компетенции.
   При срабатывании любого триггера — открыть новый ADR на миграцию чувствительных контуров на self-hosted.

## 3. Consequences (Последствия)

### Положительные (Pros):

1. **Скорость вывода на рынок:** нулевая инфраструктурная подготовка — MVP запускается за недели, а не месяцы; команда фокусируется на промптах и агентной логике, а не на GPU-стеке.
2. **Экономика MVP:** \$1.5–4K/мес против ≥ \$7.9K/мес фиксированных затрат self-hosted; расходы растут линейно с фактическим использованием, нет CAPEX [4, 7].
3. **Качество агентных сценариев:** флагманские модели надёжнее в tool calling и структурированном выводе — меньше каскадных ошибок Supervisor'а, ниже hallucination rate в RAG-ответах [5].
4. **Предсказуемая эксплуатация:** доступность, апгрейды и безопасность модели — ответственность провайдера с контрактным SLA; нет on-call по GPU для команды из 2–3 человек.
5. **Эластичность:** пиковые нагрузки (сезонность командировок) абсорбируются провайдером без закупки мощностей.

### Отрицательные и компромиссы (Cons / Trade-offs):

1. **Vendor lock-in и зависимость:** deprecation моделей, изменение цен, rate limits — вне нашего контроля; митигируется шлюзом-абстракцией и квартальными миграционными тестами, но не устраняется полностью.
2. **Данные всё же покидают периметр:** несмотря на DPA + ZDR + маскирование, остаточный риск остаётся (смена условий провайдером, юридические запросы в юрисдикции провайдера). Если регуляторно запретят — решение придётся пересматривать (см. триггеры).
3. **Latency вне нашего контроля:** деградация у провайдера в пики не управляема нами; для чат-UX приемлемо, но SLA зависит от стороннего SLA (99.x%).
4. **Стоимость растёт линейно с успехом:** при стабильном трафике ~175M токенов/день (2.2× прогноза MVP) API станет дороже self-hosted — осознанно принимаем этот риск на MVP-этапе и фиксируем ранний триггер пересмотра (100M токенов/день).
5. **Ограниченная кастомизация:** тонкая настройка (fine-tuning) на внутренних данных ограничена условиями ZDR — доступна только через методы без передачи данных провайдеру (например, локальный дообученный reranker в RAG-контура).
